# SMP integration: receiver and outbox scope

Issue [#55](https://github.com/EEET2580-2026B-Blue-Fixinh/ServiceBookingPortal/issues/55)
covers outbound delivery from SBP to SMP. The booking-event receiver (§11.7) belongs to
the booking-status notification work (Req 3.3.U2).

## Existing implementation

- `LiveSmpBookingClient` implements the catalogue, booking creation and the booking lookup
  used to verify rating eligibility. Reuse this client for outbound delivery.
- `BookingServiceImpl.createBooking` calls SMP synchronously, receives SMP's `bookingRef`,
  then saves `ServiceBooking` in the customer's regional shard.
- `ServiceBooking` in the `bookings` collection is already the local projection. Reuse it;
  introducing a second read model would require keeping two local copies consistent.
- Live cancellation currently applies a local rule because SMP has no cancellation API.
  A local cancellation response is not evidence that SMP received a change.

## Receiver work

The notification implementation owns `IntegrationController`, `IntegrationServiceImpl`,
`IntegrationExternalService`, `IntegrationInternalService` and `BookingStatusWebhookDto`.
Its scope includes:

- `POST /api/v1/integration/booking-events` and service authentication for integration routes,
  separate from customer JWT authentication. Configure the shared secret through environment
  settings; allowing an unauthenticated route alone does not authenticate SMP.
- Persistent deduplication by `eventId`, including simultaneous deliveries and retries after
  a process restart. A failed attempt must remain recoverable rather than being marked done.
- Updating the existing booking projection in its owning shard. Agree on event versions or
  an authoritative refresh so delayed events cannot overwrite a newer state.
- Persisting the notification and delivering it through the existing notification service.
  Recovery must cover a crash between updating the booking and saving the notification,
  without creating duplicate notifications.
- Updating projection freshness metadata; the booking list currently reports `createdAt`
  as its last known synchronization time.

## Remaining outbound work for #55

- Durable booking commands, stored consistently with the local creation/update intent.
- A worker with atomic claiming, bounded retries/backoff, recovery after restart, processed
  status and monitoring of outstanding count and oldest-message age.
- Reuse of `LiveSmpBookingClient`; remove the direct creation send when the worker becomes
  responsible for that command. Never send the same create once synchronously and again
  through an independent outbox entry.
- An explicit response contract for queued creation. The current API returns HTTP 201 with
  a reference generated by SMP, so switching to asynchronous creation also requires a way
  for the frontend to track the pending request until that reference exists.
- Tests for regional routing, concurrent workers, replay, restart, timeout after remote
  persistence, and failure while saving the local projection. Verify against SMP dev before
  enabling outbound retries in live mode.

## Contract prerequisite for automatic create retries

The [SMP booking controller](https://github.com/EEET2580-2026B-Blue-Fixinh/ServiceManagementPortal/blob/5ea4ece895045d34b49a833967af1c3f6c7a3146/src/main/java/com/fixinh/smt/booking/BookingController.java)
inspected on 2026-09-11 accepts neither a caller request ID nor an idempotency key.
Each accepted POST creates a booking. Unique booking references do
not deduplicate repeated requests.

Before enabling automatic retries, agree with SMP on a stable command ID and durable
idempotency: replaying the same command returns the same booking, while reuse with a
different payload is rejected. A timeout or 5xx can happen after SMP has persisted the
booking; blindly retrying such a POST can create a second job. Merely attaching an ignored
header from SBP does not solve this. Uncertain outcomes need reconciliation until SMP
supports that contract.

Receiver events and outbound commands have separate identities and retry lifecycles.
Updating a projection from an inbound event must not automatically enqueue the same change
back to SMP.

## Relation to rating issue #102

The rating form state fix is independent of synchronization. SBP renders the local status,
while a live rating submission verifies ownership and `COMPLETED` against SMP. The receiver
can address stale local status; it must not bypass the authoritative rating check.
